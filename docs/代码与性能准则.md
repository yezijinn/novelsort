# 代码与性能准则

> 适用：`novel-lines-cpp`（纯 C++20 core + Qt Widgets GUI）
> 目的：把「写对、写快、写完可验证」变成固定流程，而不是靠临场感觉。
> 基线日期：2026-10-18

---

## 0. 三条底线

1. **正确性优先。** 优化不得改变可观察行为；确需改变，先改设计和测试，再改代码。
2. **先测量，后优化。** 没有 Release 实测数据的优化，一律视为猜测。
3. **复杂度优先于常数。** 先消掉 O(n²) 和重复扫描，再谈 reserve、内联和线程。

补充两条项目硬约束：

- 业务代码只用 **C++20**；禁止 Python / JS / TS / QML / Electron / Shell 承载业务逻辑。
- `src/core` 不依赖 Qt；Qt 只出现在 `src/ui` 的 C++ 窗口层。

## 1. 动手之前

### 1.1 先定义「好」的指标

不要写「尽量快」。先写清楚输入规模、指标和上限：

| 场景 | 指标 | 当前参考基线 |
|---|---|---|
| 打开 8.7MB UTF-8 | 解析耗时 | 40–76ms |
| 打开 17.7MB GB18030 | 解析耗时 / 峰值内存 | 248–251ms / 47.5MB |
| 导出 17.7MB | 渲染 + 写盘 | 300–360ms / 峰值约 60MB |
| GUI 打开 17.7MB | 工作集 / 私有内存 | 65MB / 47.7MB |
| 预览切章 | 可感知延迟 | 目标 < 50ms |
| 列表滚动 / 选中 | 可感知延迟 | 目标 < 16ms |
| 普通编辑操作 | UI 阻塞 | 目标 < 100ms |

换机器、换编译器或换 Qt 版本后，先重测，再判断是否超线。

### 1.2 找热路径，不要平均用力

本项目真正的热路径只有几处：

- 解析：逐行判断标题，全书一次；
- 渲染：逐行输出，全书一次；
- 预览：每次切章处理一章；
- 列表绘制：只画可见的几十行；
- 批量 CLI：单文件一次。

不是热路径的地方，不要为「看起来更快」增加复杂度：主题切换、对话框、导出 JSON（几十 KB）、设置读写、右键菜单。

**判断方法**：先问「这段代码在 18MB 书上执行多少次？」  
每行一次、每章一次、每次点击一次，优化优先级完全不同。

### 1.3 先算复杂度

写之前至少回答：

- 是否有嵌套全量扫描？
- 是否在循环里做 `find`、`substr`、`QString` 转换、容器拷贝？
- 是否对每一行重新分配字符串？
- 是否对每个章节重新构建整份文档？
- 是否对每次编辑复制整张表？

本项目要求主链路保持 **O(n)**：

- 解析：一次行扫描 + 候选标题二次确认；
- 目录去重：哈希 / 计数，避免两两比较；
- 渲染：一次行扫描 + O(1) 行状态查询；
- 预览：只处理当前章；
- 列表：Qt 模型/视图虚拟化，只画可见行。

O(n²) 只在极小数据上可接受，例如几十条对话框数据；不得进入解析、渲染、预览主链路。

### 1.4 先算内存账

峰值内存通常由几部分叠加：

```
原文件字节 + 解码中间缓冲 + UTF-8 文本 + 行视图 + 章节对象 + 输出缓冲 + 撤销快照
```

写代码前要明确：

- 能不能流式/分块处理，避免「原文 + 中间 + 输出」三份同时驻留？
- 缓存有没有上限？失效键是否完整？
- 撤销/重做是不是整表复制？大书会不会无上限增长？
- 临时容器是否按最坏情况 reserve，造成大块 commit 但从不触碰？

**内存优化看峰值，不只看 steady state。**  
用工作集（Working Set）和私有内存（Private Bytes）各测一次；只测任务管理器的一个数字容易误判。

### 1.5 先定接口和边界

- core 接口不出现 Qt 类型；GUI 负责 `QString` 与 `std::string` 的边界转换。
- 输入输出用明确的所有权：只读用 `std::string_view`，需要保存才 `std::string`。
- 失败返回 `bool` + 错误信息，不靠异常穿过 UI。
- 纯函数优先：解析、渲染、重编号不依赖全局状态，便于测试和基准。
- 不静默丢字：前言、全书无标题、无效内容都要有明确处理路径。

### 1.6 写代码前先写验证

至少准备三样：

1. **正确性基线**：现有样本导出逐字节一致；新增行为有单元测试。
2. **回归用例**：这次修的 bug 必须有一个会失败的测试，再让它通过。
3. **测量命令**：Release 构建、固定输入、重复 3 次取中位数、记录峰值。

没有验证方案的「优化」，不允许直接改热路径。

### 1.7 一页设计模板

动手前用半页纸回答：

```text
目标：
输入规模：
热路径：
当前复杂度 / 目标复杂度：
当前耗时 / 目标耗时：
当前峰值 / 目标峰值：
可能的内存峰值构成：
会影响哪些不变量：
正确性验证：
性能验证：
失败时如何回退：
```

答不出来，说明还没准备好写。

## 2. 编写之中

### 2.1 语言与分层

- 统一 C++20；core 不引入 Qt、不引入第三方运行时。
- GUI 只用 Qt Widgets 的 C++ API；不引入 QML。
- CMake 只做构建配置，不承载业务逻辑。
- 新增依赖前先问：能否用标准库或现有代码在 50 行内解决？不能，再评估依赖的启动、内存和部署成本。

### 2.2 字符串：少拷贝，晚构造

- 只读文本用 `std::string_view`；不要为了「安全」每行 `std::string`。
- 需要保存到章节对象时再构造 `std::string`；构造后尽量 `std::move`。
- 禁止在逐行循环里 `substr` 只为判断前缀；先看长度和首字符，再取必要片段。
- core 内不出现 `QString`；GUI 用 `QString::fromUtf8(data, size)`，不要先转 `std::string` 再转 `QString`。
- SSO 只说明短字符串不分配，不代表可以随意复制；复制 100 万次仍然是成本。

### 2.3 容器：容量和查找方式要匹配

- 已知规模就 `reserve`；但不要对稀疏结果按总行数盲目 reserve，先测量峰值是否真的下降。
- 顺序遍历用 `std::vector`；需要有序查找优先「排序 vector + `binary_search`」，不要在热路径用 `std::map`。
- 哈希表只在确实需要键查找时使用，并 `reserve` 预期桶数；小数据（几十项）线性扫描往往更快。
- `std::vector<bool>` 用于位集合是合理的；不要为了「看起来现代」换成 `vector<char>` 让缓存变差。
- 结构体数组优先于「指针数组 + 分散对象」，减少 cache miss 和分配次数。

### 2.4 分配与拷贝

热路径的头号敌人是「每行一次堆分配」：

- 先做廉价预筛（长度、首字符、前缀），通过后再构造候选字符串。
- 解析候选只保存必要字段；不要整行复制进多个容器。
- 渲染直接写输出缓冲，不要先拼一个临时字符串再 `+=`。
- 返回大对象依赖 NRVO / move；不要 `return std::move(x)` 阻止 NRVO。
- 循环内复用缓冲区；但复用前想清楚生命周期，避免悬空 `string_view`。
- 不要用 `std::stringstream` 做逐行拼接；它适合日志和一次性格式化，不适合热路径。

### 2.5 解析与算法

本项目的固定套路：

1. **廉价预筛**：长度、首字符、是否可能是标题；
2. **精确匹配**：只对候选做完整规则判断；
3. **一次扫描**：TOC、前言、章节范围在同一次遍历中确定；
4. **有序不变量**：`skip_lines` 升序去重，`extra_body` 按源行排序并合并；
5. **直接渲染**：用行状态数组 + 章节范围，避免重复构建中间结构。

新增规则时先问：

- 会不会把对白/正文误判为标题？
- 会不会让原本 O(n) 的扫描变成每行一次区间查找？
- 规则之间的优先级是否明确？
- 误判后的恢复路径是什么（不参与排序、划转、拆分、无效内容）？

### 2.6 编码与 I/O

- 文件一次读入；编码探测和换行归一化尽量原地完成。
- 大文件解码分块，避免整份 UTF-16 中间缓冲常驻。
- 调 Win32 转换 API 时，先测量调用次数是否真的是瓶颈；**不要假设「少两次 sizing 就一定快 1.5 倍」**。本项目实测：GB18030 从 4 次调用降为 2 次，解析仍是 248–251ms，瓶颈在转换本身。
- 输出前按已知规模 `reserve`；但输出 26MB 时，几十 KB 的 JSON reserve 不是优化重点。
- 任何编码失败都要有明确错误，不得输出半份文件后静默成功。

### 2.7 GUI

- 列表用 model/view，不用「每行一个 widget」。
- 两列序号和标题在**同一个模型列**里由 delegate 绘制，保证搜索、选中、拖拽严格绑定；不要为了两列拆成两个视图。
- 列表只处理可见行；不要在 `paint()` 里做全书扫描、字符串拼接或文件 I/O。
- 预览按章构建；缓存必须有明确键（章节范围、排除区间、文本排除、extra_body、主题），并提供失效路径。
- 预览的只读是交互约束，不是性能优化；不要因此每次按键重建整章文档。
- 长操作要么分块，要么给进度/等待光标；不得让 UI 线程无响应超过 100ms 的无反馈操作。
- 撤销/重做必须有内存上限；本项目为 60 步且快照总计不超过 24MB，超限丢最旧一步，至少保留一步。

### 2.8 内存

- 缓存、历史、撤销栈都必须有上限；没有上限的容器就是内存泄漏的变体。
- 快照估算按「结构体 + 容器 capacity + 字符串 capacity」保守计算；宁可早一点裁剪，不要等到 OOM。
- 不要为了省几 KB 引入复杂对象池；先测峰值构成。
- 大字符串 `shrink_to_fit` 很少是优化，可能造成一次完整拷贝；除非测量证明空闲内存确实需要归还。

### 2.9 正确性不变量

这些不变量必须由写路径统一维护，不能靠渲染时猜测：

- `title == number + separator + name`（有编号/改名时）；
- `skip_lines` 升序、无重复；
- `extra_body` 按源行升序、无重叠；连续划转后必须重新排序合并；
- 章节范围 `start_line <= end_line`，且不越过行数；
- 导出不得丢正文；无效内容只按明确标记丢弃；
- 合成前言/全文不参与编号时，后续章节序号不得被凭空改动。

新增写操作时，先列出它会破坏哪些不变量，再决定在哪一层统一修复。

### 2.10 错误处理与测试

- 解析、编码、导出失败返回明确错误；不要用空结果冒充成功。
- 边界用例固定覆盖：空文件、无标题、只有前言、目录区、BOM、CRLF、UTF-16、GB18030、超长行、最后一章划转、首章拆分、无编号章拆分。
- 每个修复配一个回归测试；测试断言行为，不依赖实现细节。
- 性能改动也要跑正确性基线；性能不能以输出变化为代价。

## 3. 写完之后

### 3.1 必过门禁

按顺序执行，任何一项失败都不算完成：

1. Release 构建，**0 warning**；
2. core 测试全绿（当前 6855 checks）；
3. GUI 自检全绿（当前 56 项）；
4. `ctest` 全绿；
5. 现有样本导出逐字节一致（当前 133 个样本基线）；
6. 手工检查：打开、切章、搜索、拖拽、撤销/重做、导出；
7. 源码扫描：无 Python/JS/TS/QML/Shell 业务代码，根目录无临时脚本/对象文件。

### 3.2 性能测量方法

- 只测 **Release**；Debug 数据没有决策价值。
- 固定输入、固定机器、关闭无关程序；冷启动和热缓存分开记录。
- 每个场景至少 3 次，取中位数；同时记录最大值，避免偶发卡顿被平均值掩盖。
- 峰值内存用 5–10ms 轮询 Working Set；只在进程退出后读一个数会漏掉峰值。
- 分阶段测量：解析、渲染、JSON、写盘、GUI 加载、切章。不要只报一个总数。
- 对照实验：同内容的 UTF-8 与 GB18030 各跑一次，量化编码占比。本项目 25.9MB UTF-8 解析 104–107ms，17.7MB GB18030 解析 248–251ms，说明约 145ms 花在解码。
- 任何优化都要有 before/after 表；没有数据就回退。

### 3.3 审查清单

对每个改动逐条回答：

- [ ] 是否引入 O(n²)、每行/每章重复扫描？
- [ ] 是否在循环里分配、拷贝、`QString` 转换？
- [ ] 是否对每行构造 `std::string`，而 `string_view` 就够？
- [ ] 是否每次编辑都全模型 reset / 整章文档重建？能否增量？
- [ ] 缓存、撤销、历史是否有上限和失效键？
- [ ] 峰值内存是否算过「输入 + 中间 + 输出 + 快照」？
- [ ] 是否阻塞 UI 线程超过 100ms 且没有反馈？
- [ ] 多线程是否真的必要？有没有共享写、顺序依赖、线程创建开销？
- [ ] 优化后输出是否仍逐字节一致？
- [ ] 代码是否更简单？如果更复杂，收益是否已被数据证明？
- [ ] 是否补了回归测试和性能记录？
- [ ] 是否有可回退路径？

### 3.4 优化取舍

**值得做：**

- 消除主链路的重复全量扫描；
- 消除逐行/逐章堆分配和字符串拷贝；
- 给无上限的历史/缓存加内存上限；
- 把 O(n²) 查找换成排序 + 二分或哈希；
- 把「输入 + 中间 + 输出」三份常驻改成流式/分块；
- 有数据证明的 UI 卡顿点。

**通常不值得：**

- 未触碰页面的 `reserve`（不进入 RSS，只增加 commit）；
- 几十 KB 的 JSON 输出 reserve；
- `vector<bool>` 改 `vector<char>`（可能更慢）；
- 2000 行模型全 reset（约 0.5ms，先测再改）；
- 为了 1–2% 提升引入线程池、Qt6、Direct2D 或新依赖；
- 没有 profile 就重写渲染器/解析器；
- 把 UI 重绘当成算法问题。

**多线程准入条件：**

1. 确实是 CPU-bound；
2. 数据可独立分块；
3. 无共享写，或可用明确的合并顺序；
4. 顺序结果可稳定还原；
5. 线程创建/同步成本小于收益；
6. 有失败回退和内存上限。

不满足就别加。当前 18MB 书 250ms 解析，加线程的复杂度大于收益。

### 3.5 优化记录模板

每次性能改动在提交说明或文档里留一条：

```text
改动：
假设：
测量方法：
改动前：耗时 / 峰值 / 输出
改动后：耗时 / 峰值 / 输出
正确性证据：
结论：保留 / 回退
```

只写「优化了性能」没有数字，视为没有完成。

## 4. 本项目已踩过的坑

| 现象 | 教训 |
|---|---|
| GB18030 每块 4 次 Win32 调用，预期 1.3–1.5× | 实测解析仍 248–251ms；瓶颈是转换本身。先测量，再判断 |
| 连续两次「划为下一章」后正文顺序反了 | `extra_body` 只插入不排序；写路径必须维护有序、合并、无重叠不变量 |
| 撤销 60 步整表复制，大书内存上涨 | 历史必须有内存上限；普通书保留步数，大书自动裁剪 |
| 曾想把 `Candidate` 按全部行数 reserve | 未触碰页不进 RSS，实测无收益；不要优化理论峰值 |
| 预览每次切章全量建映射 | 1–3ms 级；先确认是否可感知，再决定是否做章内偏移/增量 |
| 用 `QString` 在 core 热路径转换 | core 不依赖 Qt；边界一次转换，循环内不转换 |
| 两列拆成两个视图 | 搜索/选中/拖拽会失配；单列模型 + delegate 自绘更稳 |
| 全模型 reset 看起来「很重」 | 2000 行约 0.5ms；有数据再改 `dataChanged` |

## 5. 当前基线与停止条件

当前版本已经达到实用性能，不再为「理论更快」重写架构：

- 18MB 级 GB18030 书：解析约 250ms，峰值约 47.5MB；
- 导出：300–360ms，输出 25.9MB，峰值约 60MB；
- GUI 18MB 书：工作集约 65MB；
- core 6855 checks / 0 failures；GUI 56/56。

**停止条件：**

- 主链路保持 O(n)，无每行/每章重复全量扫描；
- 18MB 书打开 < 300ms、GUI 工作集 < 80MB；
- 无上限的缓存/历史已消除；
- 优化不再带来可测量收益，或收益小于复杂度成本。

达到以上条件后，优先修正确性、边界和可维护性，不再做微优化。
